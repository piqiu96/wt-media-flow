# 模块化自媒体运营平台总体设计

日期：2026-07-06  
状态：修订设计已确认，待书面规格复核

## 1. 产品愿景

`wt-media-flow` 从视频采集、合成和发布工具演进为面向游戏视频矩阵的模块化
自媒体运营平台：

```text
账号运维
→ 热点发现
→ 素材入库与筛选
→ 视频合成
→ 人工发布
→ 增长互动
→ 数据分析
```

平台既支持完整流程，也允许独立使用任一模块。例如，运营可以不经过素材和发布
模块，直接输入任意社媒作品链接执行评论、点赞或收藏。

目标规模：

- 管理 200–500 个媒体账号。
- 每天生产和发布约 200 条视频。
- 同时运营约 10 个游戏。
- 支持 Windows 和 macOS 运营端。
- 首版优先支持百家号和 B 站发布，平台适配器可扩展。

AI 视频创作和内容拆解暂不进入首版。DeepSeek 可以用于热点总结、关键词扩展和
运营数据分析，但不能直接修改业务规则或自动生产视频。

## 2. 架构选择

采用“有边界的模块化单体”：

- 首版是一个产品、一个云端服务和一套版本。
- 每个业务模块拥有独立入口、数据、服务和接口。
- 模块可以按需启用，也可以从自身入口单独工作。
- 模块之间通过同步接口和数据库事件箱协作。
- 首版不开发插件安装器、消息队列或微服务。
- 模块边界为未来独立部署预留，但不提前承担分布式运维成本。

## 3. 总体架构

```text
云端
├── 云端控制台 Web/API
├── MySQL 共享业务数据库
├── 平台内核
│   ├── 用户与轻量权限
│   ├── 用户设备节点
│   ├── 简单任务记录
│   ├── 媒体资产
│   └── 轻量审计
├── 七个业务模块
├── 云端生产执行器
└── 云端本地磁盘

运营电脑
├── Media Platform 运营端
├── SQLite 文件数据库
├── 本地媒体文件
├── FFmpeg
└── 比特浏览器
```

云端控制台负责共享数据、全局规则、团队协作和任务汇总。运营端负责必须访问
本机文件、FFmpeg 或比特浏览器的动作。

云端生产执行器与云端控制台同机部署，但使用独立进程运行抓取、下载、FFmpeg
合成和打包，避免阻塞 Web 服务。执行器在任务记录中使用固定节点身份
`central-production`，未来可以迁移到独立机器。

## 4. 云端与本地数据边界

云端使用 MySQL，保存共享业务事实：

- 用户、设备、窗口和媒体账号。
- 热点、素材、领取、成片和发布记录。
- 互动、数据分析和关键任务记录。
- 云端成片、发布包的文件索引。

运营端使用 SQLite 文件数据库，保存：

- 本机任务和进度。
- 本机素材、成片和缓存索引。
- 尚未同步到云端的操作事件。
- 本地配置、日志位置和诊断结果。

媒体文件不写入 MySQL 或 SQLite，而是存放在云端或本地文件系统。数据库只记录
相对路径、大小和校验值。

共享业务以云端 MySQL 为准；SQLite 是本机执行状态和离线待同步操作的权威。
本地只能通过云端 API 访问共享数据，不能直接连接 MySQL。

## 5. 平台内核

### 5.1 用户与轻量权限

首版只保留两个角色：

- 运营：操作自己的账号、素材、成片、发布和互动任务。
- 管理员：管理全部用户、账号、公共配置和异常。

权限判断以“是否本人数据”或“是否管理员”为主。不实现组织树、自定义角色、
字段级权限或复杂 RBAC。

### 5.2 用户设备节点

一个用户可以登记多台 `user_node`，但同一时间只有一台主节点可以执行写操作。

正常交接：

```text
节点 A 上传待同步事件
→ 释放主节点
→ 节点 B 拉取云端最新数据
→ 节点 B 成为主节点
```

节点 A 损坏时，节点 B 可以强制接管。旧节点恢复后进入只读状态，其未同步事件
必须人工确认后才能补传。首版不实现多主写入和自动冲突合并。

### 5.3 简单任务记录

任务内核只保留：

```text
task
└── task_event
```

`task` 记录任务类型、所属模块、业务对象、用户、节点、状态、进度、起止时间、
错误和结果摘要。

状态：

```text
pending → running → success
                  ↘ failed
         ↘ cancelled
```

重试创建新任务，并通过 `retry_task_id` 关联原任务。`task_event` 只记录开始关键
步骤、完成关键步骤、失败、暂停和取消。详细 FFmpeg、网络和浏览器日志保留在
执行设备文件中。

### 5.4 媒体资产

`media_asset` 为视频、图片、封面和压缩包提供稳定身份，记录存储位置、相对路径、
大小、校验值和保留状态。业务对象不使用绝对路径作为身份。

### 5.5 轻量审计

只记录以下关键操作：

- 比特环境首次绑定审批。
- 主节点切换和强制接管。
- 账号归属或凭证更新。
- 发布状态手动修改。
- 批量互动任务创建和取消。

不记录普通页面浏览、搜索、素材领取、普通合成和下载。

## 6. 账号运维模块

### 6.1 数据关系

```text
user
├── user_node
└── browser_profile
    └── media_account
```

比特浏览器窗口位于比特云端，同一用户的不同设备看到相同窗口集合。
`browser_profile` 属于用户，不属于某台设备。

`media_account` 表示窗口中的百家号、B站等自媒体账号，并包含当前加密 Cookie
或 Token。凭证字段默认不查询、不返回明文、不写日志，只能由受控服务加解密。

### 6.2 首次绑定与后续同步

首次：

```text
运营端读取当前比特窗口集合
→ 运营强确认当前比特环境正确
→ 同步云端
→ 管理员审批用户与比特环境绑定
→ 绑定生效
```

绑定后新建窗口直接同步，不再逐窗口审批。如果原窗口整体消失且同时出现大量陌生
窗口，系统提示疑似切换比特用户，暂停敏感操作并要求重新审批。

### 6.3 媒体账号创建

支持三种方式：

1. 批量 CK 登录：导入 Cookie、写入窗口、验证登录并读取账号信息。
2. 批量验证码登录：触发验证码，调用接码/解码 API，完成登录并回填账号信息。
3. 人工登录：运营手动完成登录，再由系统读取并绑定账号信息。

三种方式最终都生成统一 `media_account`。账号支持一个主分类和多个标签，并记录
登录状态、最近成功操作、发布/互动结果和简单健康提示。

## 7. 热点策略模块

热点模块负责规则、信号源、关键词、作者监控、采集计划和爬虫策略，不负责素材
审核、领取或下载。

### 7.1 跨平台搜索

同一页面聚合展示：

- 抖音
- 快手
- B站
- 小红书
- 百度

每个平台通过独立适配器接入并标准化标题、作者、封面、发布时间、互动数据和
作品链接。平台特有字段保留在扩展数据中。

### 7.2 DeepSeek 辅助

DeepSeek 可以：

- 汇总同一热点的多平台信息。
- 生成热点摘要和时间线。
- 推荐关键词和排除词。
- 解释热点值得关注的原因。

AI 输出必须保留来源、生成时间和人工确认状态；AI 不可用时不影响原始搜索。

### 7.3 爬虫风险

每个平台独立设置限速、并发、缓存、代理和风控状态。发现 403、429、验证码或
异常空结果时自动退避或暂停，不无限重试。代理记录成功率和冷却时间。官方或
稳定数据 API 优先于浏览器和 HTTP 抓取。

热点模块输出 `content_lead`，素材模块决定其是否成为正式素材。

## 8. 素材管理模块

### 8.1 简化数据模型

```text
material
├── material_source
└── material_usage
    └── composite_output
```

- `material`：素材本体及当前审核、推荐和退场状态。
- `material_source`：素材由热点、关键词、作者、运营链接或自动规则发现。
- `material_usage`：某个用户领取和使用素材的独立记录。

审核当前值直接保存在 `material`，不设置独立 `material_review`。关键审核修改
需要时写入轻量审计。

所有外键使用完整表名加 `_id`，例如 `material_id`、`material_usage_id`、
`composite_output_id`，不使用含糊的 `usage_id` 或 `output_id`。

### 8.2 入库和去重

来源包括热点线索、跨平台搜索、作者监控、运营粘贴链接和云端自动生产。

主去重键：

```text
(platform, source_vid)
```

同一素材被多个渠道发现时只创建一个 `material`，新增 `material_source`。
这样可以分析关键词、热点和作者带来的素材质量。

### 8.3 审核、领取与退场

素材支持通过、拒绝、暂缓、推荐、降权、暂停和退场。退场只停止新领取，不删除
历史。

同一素材可被多个用户领取；同一用户对同一素材只有一条 `material_usage`。
再次领取时恢复原记录。每个用户的下载、合成、评价和放弃互不影响。

运营可以批量选择多条素材加入合成池。未领取素材自动创建 `material_usage`；
已存在相同配置成片或运行中任务时汇总提醒。

### 8.4 自动生产通道

云端自动规则可以跳过人工筛选，但不能跳过去重、链接有效性和基础安全检查。
自动素材创建系统使用记录后直接进入云端合成。

## 9. 视频合成模块

合成不绑定游戏、媒体平台或账号分类。输入视频使用运营专属或公共
`composite_strategy`。

### 9.1 输入与执行位置

支持：

- `material_usage`。
- 本地视频文件。
- 可解析的外部视频链接。

本地合成由运营端执行，云端自动生产由 `central-production` 执行。两者使用相同
策略模型。

### 9.2 合成策略

策略归属优先级：

```text
运营专属策略
→ 公共策略
```

策略包含引导视频、插入范围、截尾、时长、贴纸、尾部动画、裁切、速度、亮度、
对比度、分辨率和编码等规则。每次合成保存策略版本、随机种子和完整参数快照。

运营端登录后同步当前用户可用策略及资源到 SQLite 和本地文件系统。已完整同步的
策略可以离线使用。

### 9.3 成片与素材信息

一个 `material_usage` 可以生成多个 `composite_output`，每次可选不同策略。
成片保存素材元数据快照和可编辑发布元数据，使发布时可以直接引用标题、描述、
标签、封面、作者、热点和来源链接。

### 9.4 重复合成

使用 `config_hash` 检查输入、策略版本和关键参数：

- 相同配置已有可用成片：默认查看已有成片，允许明确创建新版本。
- 相同配置正在运行：阻止重复提交。
- 技术失败重试：复用原成片记录，只创建新任务。
- 不同策略或 A/B 版本：创建新成片。

## 10. 人工发布模块

### 10.1 多平台、多账号

成片不绑定平台。同一 `composite_output` 可以创建多条 `publication`：

```text
composite_output
├── publication → 小红书账号 A
├── publication → 百家号账号 B
└── publication → B站账号 C
```

每条发布记录拥有独立平台、账号、标题、标签、封面、状态和作品链接。

### 10.2 发布计划

`publish_plan` 表示某运营在一个批次中要将哪些视频发布到哪些账号。
每个“成片 × 媒体账号”创建一条 `publication`。计划状态由所有发布条目汇总。

### 10.3 两种发布方式

本地辅助发布：

```text
打开目标比特窗口
→ 上传视频并填写表单
→ 运营确认提交
→ 回填结果
```

发布包：

```text
云端按账号分配成片
→ 生成压缩包
→ 运营从云端下载
→ 人工发布、评论和回填状态
```

### 10.4 去重发布包

压缩包使用公共媒体目录，同一成片只存一份：

```text
publish-batch.zip
├── videos/
├── covers/
├── accounts/
│   ├── 小红书-账号A.xlsx
│   └── 百家号-账号B.xlsx
└── manifest.xlsx
```

账号清单引用 `videos/` 中的相对路径。按文件校验值去重，避免同一成片分配多个
账号时重复打包 MP4。

## 11. 增长互动模块

模块支持对系统发布记录或任意作品链接执行评论、点赞和收藏。所有浏览器操作只能
在运营本地主节点执行，云端只保存任务、话术和结果。

### 11.1 简化模型

```text
comment_template

engagement_task
└── engagement_action
```

`engagement_task` 同时保存目标作品和本次互动配置。批量导入通过 `batch_key`
分组，不增加批次表。

`engagement_action` 表示某个 `media_account` 对目标执行一个具体动作，独立记录
最终评论文本、状态和错误。

不设置每日评论、点赞或收藏额度，但保留重复检查、可配置间隔、连续失败暂停和
用户停止能力。

### 11.2 话术模板

评论必须使用公共或运营专属话术模板，也允许执行前人工替换。系统避免同一目标
重复使用相同文本，并记录最终实际发送内容。

本地执行器逐个打开比特窗口，串行完成动作并回传结果。

## 12. 数据分析模块

首版聚焦七组经营指标：

1. 产量：发布数、人均发布数、账号利用率。
2. 播放效能：总播放、单条中位播放、每百条视频带来的播放。
3. 爆款质量：爆款数、爆款率、点赞率和爆款贡献占比。
4. 生产漏斗：素材到数据回收的完成率、耗时和瓶颈。
5. 爆款复制：复制数量、再次爆款率和播放衰减。
6. 热点响应：发现热点到首条发布的耗时。
7. 竞品跟进：竞品异常增长作品和我方跟进表现。

固定页面：

- 产量与播放。
- 效能与目标。
- 爆款分析与复制。
- 端到端漏斗与瓶颈。
- 竞品监控与热点跟进。

爆款采用平台可配置的固定门槛和相对门槛组合。不同平台、账号和时间窗口不能
直接比较绝对播放量。

## 13. 爆款复制

跨平台发布直接复用现有成片并新增 `publication`。

同平台矩阵复制默认采用：

```text
原始素材
+ 爆款相同合成策略
+ 新随机种子
→ 新 composite_output
→ 分配同平台其他账号
```

随机变化包括插入点、截尾、贴纸、尾部动画、裁切、亮度、速度和封面等策略允许
的范围。数据库保存 `source_publication_id`、`viral_composite_output_id`、
`composite_strategy_id`、策略版本、随机种子、实际配置和 `batch_key`。

只有原素材丢失或无法恢复时，才允许在爆款成片基础上二次加工。

## 14. 命名规范

- 表自身主键统一为 `id`。
- 外键统一为完整表名加 `_id`。
- 特殊语义关联增加前缀，例如 `source_publication_id`。
- 普通字段保持简洁，例如 `status`、`config`、`error`。
- 不使用 `usage_id`、`output_id`、`account_id` 等含糊外键。

核心表：

```text
user
user_node
browser_profile
media_account
media_asset
task
task_event
audit_log

material
material_source
material_usage
composite_strategy
composite_output
publish_plan
publication
publish_package
publish_package_item
comment_template
engagement_task
engagement_action
tracked_object
metric_snapshot
```

## 15. 错误处理原则

- 单个作品、账号或平台失败不阻断整个批次。
- 页面展示失败发生在哪一步、简短原因和是否可重试。
- 发布或互动结果不确定时进入待核实，不能自动重复执行。
- 云端断网时，本地只处理已缓存工作；恢复后上传 SQLite 待同步事件。
- 平台适配器连续异常时暂停该平台，避免无限重试。
- 云端或本地磁盘不足时停止领取新媒体任务。
- 文件校验失败时不进入下一环节。

## 16. 测试策略

- 单元测试：状态、去重、账号匹配、策略匹配和数据汇总。
- 数据库测试：唯一约束、外键、主节点接管和本地同步。
- 集成测试：云端 API、SQLite、MySQL 和生产执行器。
- 媒体测试：损坏文件、不同编码、磁盘不足和 FFmpeg 失败。
- 浏览器测试：窗口同步、三种上号方式、发布和互动流程。
- 故障测试：断网、进程崩溃、设备切换和结果不确定。
- 试运行：先用少量用户、账号和一个游戏验证，再逐步扩容。

## 17. 建设顺序

1. 云端 MySQL、本地 SQLite、用户节点、任务、资产和一键启停。
2. 比特窗口同步、账号创建、凭证和账号健康。
3. 素材、领取、批量合成池、策略同步和本地合成。
