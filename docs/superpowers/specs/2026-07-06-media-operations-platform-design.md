# 游戏自媒体矩阵运营平台设计

日期：2026-07-06  
状态：设计已确认，待用户复核书面规格

## 1. 背景与目标

`wt-media-flow` 已具备抖音素材采集、FFmpeg 视频合成、发布计划、百家号与
B 站发布、基础评论任务和实验性 FastAPI API。本设计在现有能力之上增加中央
控制面、运营本地工作台和机器人节点，形成可供非技术运营人员使用的完整流程：

```text
热点发现 → 素材入库与筛选 → 运营领取 → 视频合成
        → 人工确认发布 → 矩阵评论 → 效果回流
```

目标规模：

- 管理 200–500 个账号。
- 每天生产和发布约 200 条视频。
- 同时运营约 10 个游戏，每个游戏每天 20–30 条候选或成片。
- 支持 Windows 和 macOS 运营节点。
- 首版发布平台为百家号和 B 站。
- 游戏、关键词、账号分类、评分阈值和合成风格均可配置。

首版面向内部团队，不做多租户 SaaS，不追求完全无人值守。发布前必须由运营
人工确认；热点采集、素材预筛、机器人合成和矩阵交叉评论可以自动执行。

## 2. 设计原则

1. 中央保存业务事实，本地保存执行现场。
2. 复用现有 workflow、平台适配器和 FFmpeg 合成能力。
3. 运营只使用 Web 界面，不要求记忆 CLI、参数或数据库 ID。
4. 中央管理工作台和本地执行工作台职责分离，但使用一致的交互语言。
5. 外部平台变化被限制在采集适配器和发布适配器内。
6. 首版使用 PostgreSQL 任务表轮询，不引入消息队列。
7. 任务可恢复、可重试、可审计，发布结果不明确时绝不自动重发。
8. 数据模型保持简单，避免为尚未验证的需求提前增加层级。

## 3. 总体架构

采用“中央控制面 + 混合执行节点”。

```text
抖音 / B站 / 外部榜单 / 人工关键词
                    ↓
中央控制面
├── 热点聚合与评分
├── 素材入库、审核与推荐
├── 账号分类、运营归属与比特用户绑定
├── 发布计划与任务调度
├── 节点租约、状态汇总与异常处理
├── 发布、评论与效果数据
├── 中央管理工作台
└── PostgreSQL 权威数据库
                    ↓
               统一任务 API
          ↙                         ↘
运营节点                              机器人节点
├── 本地执行工作台                    ├── 自动领取任务
├── 主动领取素材                      ├── 高分素材自动选取
├── 下载、合成与预览                  ├── 下载与批量合成
├── 比特浏览器发布                    └── 回传成片与状态
└── 自动评论
```

中央控制面负责账号归属、素材身份、任务分配、任务锁和最终结果，不保存账号
Cookie 或比特浏览器登录环境。节点主动连接中央并领取任务，中央不反向直接操控
运营电脑。

### 3.1 中央管理工作台

供内容负责人和管理员使用：

- 查看热点、搜索词、作者监控和公共素材池。
- 集中批量审核素材。
- 管理游戏、账号分类、标签和运营归属。
- 查看所有节点、任务、发布和评论结果。
- 处理失败、重新分配、身份换绑和审计。

### 3.2 运营本地工作台

在 `127.0.0.1` 提供页面，负责访问本机文件、FFmpeg 和比特浏览器：

- 查看可领取素材及推荐依据。
- 查看“我的素材”“我的成片”和“待发布”。
- 粘贴抖音链接或按推荐词主动搜索素材。
- 下载、单条或批量合成、预览、拒绝和重新合成。
- 发布前确认并打开对应比特浏览器容器。
- 查看自动评论、缓存和诊断状态。

### 3.3 机器人节点

机器人节点使用与运营节点相同的任务协议，不要求日常人工界面。它根据中央
规则选择高分素材，执行下载和批量合成，成片仍进入运营的发布确认池。

## 4. 素材发现与入库

素材通过三种入口汇入同一个中央筛选库。

### 4.1 推荐词主动挖掘

中央根据热点生成或维护推荐搜索词。运营可以查看推荐原因、选择关键词执行
抖音搜索、勾选结果入库，也可以自行输入关键词。系统记录提交运营、游戏、
关键词和搜索批次，用于后续评估关键词质量。

### 4.2 热门作者自动监控

内容负责人按游戏维护作者观察名单。中央定时发现作者新作品，获取作品元数据，
执行游戏匹配、时效、重复和风险预筛，再送入统一筛选库。连续低质量的作者可以
降权或暂停监控。

### 4.3 复制链接入库

中央和本地工作台都提供粘贴链接入口，但共用中央入库 API：

```text
本地或中央粘贴链接
→ 解析作品
→ 按来源平台和作品 ID 去重
→ 补全作者、标题和互动数据
→ 绑定提交运营和目标游戏
→ 进入筛选库
```

普通运营主要从本地工作台提交；内容负责人可在中央批量导入。断网时，本地将
链接放入“待提交”列表，联网后再提交中央。素材获得中央 ID 前不能正式进入
下载、合成和发布流程。

若作品已存在，系统不重复创建素材，只新增提交来源或领取意向记录。

## 5. 素材评分、审核与退场

每条素材生成可解释的推荐分：

```text
推荐分 =
  热度分
+ 时效分
+ 跨平台一致性
+ 游戏匹配度
+ 历史同类表现
+ 运营反馈
- 重复度
- 风险分
- 使用饱和度
```

评分按游戏配置阈值：

- 高分且低风险：自动进入可领取池。
- 中间区间或低置信度：进入集中批审。
- 低分、违规、严重重复或过期：自动淘汰。

内容运营可以批量通过、拒绝、修改游戏和标签，查看评分依据与相似素材，并标记
画质、违规、过时等原因。

素材生命周期：

```text
待发现 → 待解析 → 已入库 → 待评分
                     ├→ 自动通过 → 可领取
                     ├→ 待人审 → 可领取/已拒绝
                     └→ 自动淘汰

可领取 → 热门推荐 → 降权 → 暂停推荐 → 已退场
```

退场使用软删除，保留所有领取、成片、发布和效果历史。达到复用上限、热点过期、
多人放弃或发布效果持续较差均可触发降权或退场。

## 6. 素材领取与本地操作

领取不是独占素材，而是为某个运营创建一次使用关系。一个素材可被多个运营领取；
同一运营对同一素材只能有一条有效领取记录。

```text
公共素材
├── 运营 A 的 material_usage
├── 运营 B 的 material_usage
└── 机器人使用的 material_usage
```

再次遇到已领取素材时，页面显示“查看我的素材”或“继续制作”，不再重复创建记录。
已放弃或归档的记录可以恢复；新的运营周期确有需要时才创建新记录。

本地工作台包含：

1. **可领取素材**：中央素材元数据、在线预览和筛选。
2. **我的素材**：待下载、下载中、已下载、待合成和失败状态。
3. **我的成片**：播放、通过、拒绝、删除和重新合成。
4. **待发布**：已通过成片审核并分配给本人账号的任务。

本地文件下载完成后可离线查看和合成。本地保存轻量索引与待回传事件；中央始终
保存权威业务记录。

## 7. 简化数据模型

核心关系保持为：

```text
material 1:N material_usage
material_usage 1:N composite_output
composite_output 1:N publication
publication 1:N performance_snapshot
```

### 7.1 `material`

公共原素材，记录来源平台、作品 ID、作者、标题、游戏、互动数据、评分、审核和
退场状态。原素材身份不依赖文件路径。

### 7.2 `material_usage`

运营或机器人领取素材后的独立使用记录，至少关联：

- `material_id`
- `operator_id` 或机器人身份
- 领取、下载、合成和放弃状态
- 运营评价与放弃原因
- 创建时间、归档时间和当前使用周期

一个运营使用失败或放弃，不影响其他运营的使用记录。

### 7.3 `composite_output`

一次有业务意义的成片版本。一个 `material_usage` 可以拥有多个成片，用于不同
平台、风格和 A/B 方案。记录：

- 目标平台和风格模板。
- 合成参数快照。
- 文件资产 ID、校验值、时长和大小。
- 成片审核状态。
- 可选 `batch_key`。
- 可选 `experiment_key` 和 `variant`。

技术性失败重试由通用执行任务记录，不额外创建成片。只有平台、模板、参数或
实验方案发生业务变化时才创建新的 `composite_output`。

### 7.4 `publication`

成片发布到某个具体平台账号的记录，包含账号、平台、发布时间、链接、发布状态、
错误和过审状态。每次发布独立存在，不能用成片状态代替发布状态。

### 7.5 `performance_snapshot`

按时间保存播放、点赞和评论等效果数据。中央可以从任意效果快照追溯到发布、
成片、运营领取、原素材、作者、关键词和热点。

素材汇总指标不简单累加跨平台播放量，而是比较其相对同平台、同游戏、同账号
分类的基准表现。

## 8. 平台风格与多次合成

领取本身不绑定平台。运营创建成片时选择目标账号或目标平台，系统根据平台和账号
分类推荐风格模板：

```text
同一个 material_usage
├── 百家号资讯风格成片
├── 百家号攻略风格成片
└── B站攻略风格成片
```

机器人根据当日平台内容缺口、账号分类和模板规则自动选择。每个成片保存完整参数
快照，确保能够解释其生成方式并比较不同风格效果。

## 9. 账号矩阵与比特浏览器绑定

账号归属链为：

```text
系统运营用户 operator
→ 比特浏览器用户/工作空间 bit_user
→ 浏览器容器 bit_profile
→ 平台账号 platform_account
```

约束：

- 一个运营同一时间绑定一个有效的比特用户或工作空间。
- 一个比特用户包含多个浏览器容器。
- 一个容器可登录多个不同平台账号。
- 同一容器内同一平台默认对应一个账号。
- 一个平台账号同一时间只能绑定一个容器。
- 容器业务唯一性至少包含 `(bit_user_id, bit_profile_id)`。
- 换绑必须由中央管理员明确批准并保留审计记录。

节点启动和发布前都必须读取当前比特用户，并与中央绑定比较。身份不一致时停止
账号同步、发布和评论。系统不得因切换比特用户后发现新容器而覆盖旧关系。

账号采用一个主分类和多个标签，可描述游戏、账号角色、内容方向和风险状态。账号
还具有每日发布/评论额度及新号、正常、冷却、禁用等状态。

## 10. 发布与评论

发布任务按以下条件分配：

- 游戏和账号主分类匹配。
- 平台与成片版本匹配。
- 账号存在当日剩余额度。
- 原素材未在该账号重复发布。
- 满足同类内容发布间隔。
- 账号状态正常且对应运营节点在线。

成片进入本地“待发布”后，运营必须播放并点击确认，系统才打开精确匹配的比特
容器并执行平台表单自动化。

首版自动评论仅做矩阵账号交叉评论。评论账号必须与目标视频平台一致、分类或标签
匹配、不是发布账号本身、状态正常、未超过额度，且最近没有与目标账号形成固定
重复互动组合。评论随机延迟执行，连续失败触发账号冷却。

后续阶段再增加发布账号自动回复真实用户评论。

## 11. 业务状态与执行任务

业务状态回答“内容处于哪个阶段”，执行任务回答“某次后台动作是否可靠完成”。

运营可见的使用链：

```text
已领取 → 待下载 → 已下载 → 待合成 → 合成中
       → 待预览 → 成片通过 → 待发布 → 已发布
```

异常分支包括已放弃、下载失败、合成失败、成片拒绝、发布失败和发布结果待核实。

所有需要节点异步执行的动作使用统一执行状态：

```text
pending → leased → running → succeeded
                    ↘ failed → retrying
                    ↘ cancelled
```

适用动作包括热点采集、素材解析、下载、合成、发布、评论和效果回收。

中央视角关注节点、租约、尝试次数、积压和重新分配；本地视角显示下载速度、
FFmpeg 进度、文件位置、比特身份和可执行按钮。运营界面显示业务语言，不直接暴露
技术状态码。

## 12. 任务可靠性与错误处理

- 节点领取任务后获得限时租约并定期续租。
- 每个关键操作带幂等键，重复请求不产生重复业务结果。
- 下载、合成、发布、评论和效果回收分别重试。
- 节点断网时将事件写入本地日志，联网后按序补传。
- 租约过期后中央先检查结果校验值，再决定是否重新分配。
- 发布结果不明确时进入 `verification_required`，禁止自动重发。
- 中央可以暂停游戏、运营、节点、账号或特定任务类型。

以下情况强制阻断发布和评论：

- 当前比特用户与中央绑定不一致。
- 浏览器容器不属于绑定的比特用户。
- 平台账号与计划不匹配。
- 任务租约失效。
- 账号冷却或禁用。
- 成片未经过人工发布确认。
- 无法确认上一轮发布是否成功。

## 13. 媒体存储

原视频和成片通过稳定 `asset_id` 管理，而非依赖本机绝对路径。资产可位于：

- 运营节点本地缓存。
- 机器人节点本地磁盘。
- NAS。
- 对象存储。

中央保存资产类型、位置、校验值、大小和保留策略。机器人生成的共享成片优先放
NAS 或对象存储；运营自行合成的成片可以先留本机。发布完成并超过保留期后，
节点自动清理缓存，但中央业务关系和效果数据继续保留。

## 14. 安装、启动与升级

中央使用 FastAPI 和 PostgreSQL，媒体放独立磁盘、NAS 或对象存储。数据库每日
备份，升级前自动备份并执行迁移。

Windows 和 macOS 节点提供：

- “启动运营工作台”
- “停止运营工作台”
- “查看诊断信息”

启动过程检查 Python 环境、中央连接、FFmpeg、磁盘空间、比特浏览器用户和版本
兼容性，然后启动本地服务并打开浏览器。重复启动不会产生多个实例；关闭浏览器
不停止后台任务。

节点升级失败时保留旧版本并允许回退。中央和节点通过协议版本判断兼容性，禁止
不兼容节点领取任务。

## 15. 测试策略

- 单元测试：评分、素材复用、账号匹配、评论筛选和状态转换。
- 数据库测试：并发领取、任务租约、幂等、运营与比特用户换绑审计。
- 集成测试：中央 API 与模拟运营/机器人节点的完整交互。
- 媒体测试：多编码、损坏文件、超长视频、磁盘不足和 FFmpeg 失败。
- 平台测试：测试账号验证百家号和 B 站页面流程。
- 故障测试：断网、节点崩溃、中央重启、租约过期和重复回调。
- 试运行：先以 1 个游戏、2 名运营和 10–20 个账号验证，再逐步扩容。

## 16. 分阶段交付

### 阶段一：中央基础与本地工作台

- PostgreSQL 中央数据模型和迁移路径。
- 运营、比特用户、容器和平台账号强绑定。
- 中央管理工作台与本地执行工作台骨架。
- Windows/macOS 一键启停和诊断。
- 中央 API、节点注册、心跳和基础任务租约。

### 阶段二：热点与素材闭环

- 推荐词搜索、作者监控和复制链接入库。
- 评分、批审、公共素材池和素材退场。
- 多运营领取、反馈和本地下载。

### 阶段三：多版本合成

- 复用现有合成 workflow。
- 平台风格模板、参数快照和多成片。
- 机器人自动选材与批量合成。
- 成片预览、审核和发布确认池。

### 阶段四：矩阵发布与评论

- 百家号、B 站发布任务分配。
- 比特身份强校验和人工确认发布。
- 按账号主分类与标签执行矩阵交叉评论。
- 失败冷却、人工核实和结果汇总。

### 阶段五：效果反馈

- 发布效果快照。
- 素材、作者、关键词、模板和账号分类分析。
- 可解释推荐分更新及自动降权/退场。

## 17. 首版非目标

- 小红书发布实现。
- 面向外部客户的多租户 SaaS。
