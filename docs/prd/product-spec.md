# wt-media-flow 产品说明书

> 面向对象：产品、运营、内容负责人、工程维护者  
> 当前阶段：MVP 已跑通，下一步目标是把系统打磨成“简单、够用、好用”的日常运营产品。

## 1. 产品概述

`wt-media-flow` 是一个面向游戏内容矩阵运营的视频自动化工具，覆盖从素材采集、视频合成、发布计划、平台发布、评论互动到过审检查的完整链路。

一句话定位：把“找素材、做视频、分账号、发平台、补评论、查结果”这些重复运营动作，沉淀成可批量执行、可追踪、可恢复的流水线。

它解决的核心问题：

- 素材生产依赖人工搜索、下载、整理，效率低且容易重复。
- 多账号矩阵发布需要人工记账号、记配额、记视频，容易漏发或重复发。
- 发布后链接、评论、过审状态分散在平台后台，无法形成统一任务闭环。
- 新平台、新账号、新品类扩展时，容易把平台差异散落到各处，维护成本高。

当前 MVP 已经能支撑日常跑通：

```text
采集素材 -> 下载入库 -> 视频合成 -> 创建发布计划 -> 单账号批量发布
         -> 发布链接回填 -> 评论任务 -> 过审检查/通知 -> 数据统计/打包
```

下一阶段的产品目标不是“大而全”，而是先让运营每天能少想、少查、少拼命令：打开系统就知道今天要做什么、哪个账号还没发、失败了该点哪里恢复、下一步该执行什么。

## 2. 目标用户与使用场景

### 2.1 运营人员

运营人员是最主要用户，负责每天执行内容矩阵的采集、发布、评论和检查。

典型场景：

- 早上创建当天发布计划，确认每个账号分到多少条内容。
- 按账号执行发布任务，在浏览器里人工确认发布。
- 查看哪些账号失败、哪些内容待重试。
- 批量执行评论任务，补齐互动。
- 次日检查已发布内容是否过审。

运营最需要的是清晰的“今日待办”和低心智负担的操作入口。

### 2.2 内容负责人

内容负责人关注内容供给是否充足、各品类发布是否均衡、账号矩阵是否健康。

典型场景：

- 查看素材池和合成池是否够当天发布。
- 查看不同游戏品类的内容分布。
- 查看计划完成率、失败率、过审率。
- 决定是否需要扩充账号、调整品类、增加素材采集关键词。

### 2.3 工程维护者

工程维护者负责平台适配、任务稳定性、异常恢复、部署和数据维护。

典型场景：

- 接入新平台或修复平台发布页面变更。
- 优化发布、评论、过审检查的自动化稳定性。
- 维护数据库、配置、外部工具和比特浏览器连接。
- 给运营提供更易用的 Web/API/命令入口。

## 3. MVP 当前能力

本章区分“已用于日常主流程”和“已有代码但仍需运营验证”的能力。采集、合成、
发布计划和百家号/B 站发布属于当前主流程；评论和 Web API 仍为实验性能力。

### 3.1 素材采集

系统通过 `claw` 命令从抖音采集素材，支持按关键词、按品类配置、按单条链接入库。采集结果会写入素材表，记录标题、标签、来源链接、远程视频地址、封面、发布时间和热度数据。

已具备能力：

- 按关键词或品类批量采集。
- 素材去重，避免同一来源视频重复入库。
- 支持两阶段模式：先入库，后下载。
- 下载失败可重试。
- 素材按品类归档，便于后续分配给对应账号。

产品价值：运营不需要手动找视频、复制链接、下载文件，系统可以批量沉淀素材库。

### 3.2 视频合成

系统通过 `composite` 命令把采集素材加工成可发布视频。核心处理包括下载原视频、插入引导视频、截尾去重、时长控制、贴纸/尾部动画叠加、水印处理等。

已具备能力：

- 按单个 `vid` 合成。
- 批量 `vids` 合成。
- 按最近采集内容重合成。
- 支持不同品类引导视频。
- 合成结果写入 `video_tasks`，作为后续发布计划的候选内容。

产品价值：把“素材”变成“可发布内容”，并通过去重和模板化加工降低重复内容风险。

### 3.3 发布计划

系统通过 `plan create` 创建发布计划，把已合成内容分配到账号。计划会考虑账号所属用户、账号平台、账号标签、每日发布上限、视频池和品类匹配。

已具备能力：

- 按运营用户创建当天计划。
- 按账号每日限额分配内容。
- 按平台区分可用内容，支持同素材面向不同平台扩展。
- 按账号标签匹配对应品类内容。
- 支持 dry-run 预览，不写入数据库。
- 通过 `plan list` 查看计划整体状态。

产品价值：把“今天每个账号发什么”从人工记忆变成系统分配，减少漏发、重复发和分配不均。

### 3.4 发布执行

系统通过 `plan run --plan-id <N> --account-id <M>` 执行某个计划下某个账号的待发布内容。发布过程会打开比特浏览器容器，通过 Playwright 自动填充平台发布页，再由运营人工确认提交。

已具备能力：

- 单账号批量发布，一次浏览器 session 处理多条任务。
- 自动上传视频、填标题、处理封面等平台差异。
- 支持百家号人工确认模式。
- 支持 B 站基础发布能力，部分字段仍需人工确认。
- 发布成功后回填链接。
- 发布成功后可创建评论任务。
- 发布结果可推送企微通知。

产品价值：运营不再逐条准备素材和填写表单，只需要在浏览器里做最后确认。

### 3.5 评论互动（实验性）

系统通过 `comment` 命令处理评论任务。发布成功并拿到链接后，系统可以按品类从话术库抽取评论内容，并使用不同账号执行评论。

代码已具备能力：

- 单条评论。
- 按账号批量处理评论队列。
- 随机多账号评论。
- 按品类读取评论话术模板。
- 评论结果写回任务状态。

当前状态：数据库尚无稳定评论任务数据，不能视为已经跑通的日常流程。

### 3.6 过审检查与数据统计

系统通过 `plan check` 检查已发布链接是否可访问，并对已过审内容做通知标记。系统也提供 `plan stats` 抓取已发布内容的播放、点赞、评论等数据。

已具备能力：

- 按计划检查未通知的已发布链接。
- 优先使用浏览器检查，缺少浏览器时降级为 HTTP 检查。
- 过审后发送企微通知。
- 抓取已发布视频的数据统计字段。

产品价值：让“发布是否真正可见”成为可追踪状态，而不是完全依赖人工打开后台检查。

### 3.7 打包与手动发布兜底

系统通过 `pack` 命令把某个发布计划的视频、封面、标题清单打包成 zip，供运营手动发布或迁移使用。

已具备能力：

- 按计划或账号打包视频和封面。
- 生成账号目录和 manifest 清单。
- 可选 AI 生成三平台标题。

产品价值：当自动化发布不稳定或平台临时变化时，运营仍有可落地的手动发布包。

### 3.8 Web API（实验性）

系统提供 FastAPI 服务，通过 `serve` 启动。当前 API 主要用于开发和后续工作台验证，
日常操作仍以 CLI 为准。

代码已提供：

- 查询和创建计划。
- 查询计划详情。
- 后台触发单账号发布。
- 查询视频任务列表。
- 查询和处理素材审核。
- 查询账号和平台能力。

当前状态：接口缺少完整运营验证、鉴权和持久化任务队列，暂不作为稳定生产入口。

## 4. 核心业务流程

### 4.1 每日运营主流程

```text
1. 采集素材
   运营按品类或关键词采集抖音素材，系统入库并下载。

2. 合成视频
   系统将素材加工成带引导、去重处理、可发布的视频任务。

3. 创建计划
   系统按用户、账号、平台、品类和每日限额生成发布计划。

4. 执行发布
   运营按账号执行计划，系统自动填表，运营人工确认提交。

5. 回填链接
   系统获取发布后的链接，并把计划条目标记为发布成功。

6. 执行评论（实验性）
   在具备有效评论任务时，运营可按账号批量完成互动。

7. 检查过审
   次日或稍后检查链接是否可访问，过审后通知。

8. 查看统计
   抓取播放、点赞、评论等数据，为内容和账号调整提供依据。
```

### 4.2 运营日常命令入口

常用命令包括：

```bash
.venv/bin/python3 src/main.py claw --category 三角洲 --config conf/claw.yaml
.venv/bin/python3 src/main.py composite --recomposite --config conf/composite.yaml --category 三角洲
.venv/bin/python3 src/main.py plan create --user-id <用户ID> --dry-run
.venv/bin/python3 src/main.py plan create --user-id <用户ID>
.venv/bin/python3 src/main.py plan list
.venv/bin/python3 src/main.py plan run --plan-id <计划ID> --account-id <账号ID>
.venv/bin/python3 src/main.py comment batch --account-id <账号ID>
.venv/bin/python3 src/main.py plan check --plan-id <计划ID>
```

当前问题是：这些命令已经能完成工作，但运营仍需要知道很多参数、ID 和执行顺序。下一阶段应把这些命令背后的能力收敛成“今日工作台”和“下一步操作建议”。

## 5. 数据与状态模型

### 5.1 `videos`：素材资产

`videos` 是素材层，记录从外部平台采集来的原始视频及其元数据。

产品含义：

- 表示“可被加工的原始素材”。
- 关注来源、标题、封面、热度、品类、下载状态和审核状态。
- 去重依据主要来自来源平台和来源视频 ID。

典型状态：

- `claw_status=pending`：已入库，待下载。
- `claw_status=done`：已下载。
- `claw_status=failed`：下载失败，需重试。
- `review_status=approved/rejected`：内容审核结果。

### 5.2 `video_tasks`：合成产物

`video_tasks` 是内容生产层，记录某个素材被加工成可发布视频的过程和结果。

产品含义：

- 表示“已经或正在生产的发布素材”。
- 合成完成后才会进入发布计划候选池。
- 发布阶段不再以它作为权威状态，发布状态由 `plan_items` 管理。

典型状态：

- `pending`：待合成。
- `compositing`：合成中。
- `composited`：合成完成，可进入计划。
- `failed`：合成失败。

### 5.3 `publish_plans`：发布批次

`publish_plans` 是计划层，表示某一天或某一批次的发布任务集合。

产品含义：

- 表示“今天/本批次要发布的一组任务”。
- 归属某个运营用户。
- 运营查看计划时，首先看这一层。

典型状态：

- `pending`：已创建，未开始执行。
- `running`：部分账号或任务正在执行。
- `done`：计划已结束或人工标记完成。

### 5.4 `plan_items`：单条发布任务

`plan_items` 是发布执行层，表示“某账号发布某条视频”的具体任务。

产品含义：

- 是发布成功、失败、重试、回链、统计的核心追踪对象。
- 同一个计划下，一个账号会有多条 `plan_items`。
- 运营真正执行的是某个账号的一组 `plan_items`。

典型状态：

- `pending`：待发布。
- `publishing`：发布中。
- `published`：发布成功，通常已回填链接。
- `failed`：发布失败，需要查看原因并决定是否重试。

### 5.5 `comment_tasks`：评论任务

`comment_tasks` 是互动层，表示“某个账号对某条已发布内容进行评论”的任务。

产品含义：

- 发布成功后自动或半自动生成。
- 评论文案可按品类从话术库抽取。
- 评论账号应尽量不同于发布账号。

典型状态：

- `pending`：待评论。
- `commenting`：评论中。
- `done`：评论完成。
- `failed`：评论失败。

## 6. 当前不足

### 6.1 易用性不足

系统能力已经跑通，但主要通过 CLI 暴露。运营需要记住命令、参数、用户 ID、账号 ID、计划 ID，还要自己判断下一步该做什么。

表现：

- 创建计划后，需要手动查询账号列表和待执行数量。
- 执行计划时，需要人工拼 `plan run` 命令。
- 多账号执行顺序、剩余任务、失败任务不够直观。
- 运营很难一眼判断“今天还差什么”。

### 6.2 状态可视化不足

计划、视频、评论、过审、统计都已有数据结构，但没有统一看板承载。

表现：

- `plan list` 只能看到总数、成功、失败、待执行。
- 单个账号的任务明细需要额外查询或写 SQL。
- 失败原因分散在日志和数据库字段中。
- 评论任务、过审状态、统计数据没有形成统一运营视图。

### 6.3 异常恢复不够直观

系统支持重置失败任务和重试下载，但运营侧缺少清晰的失败分类和处理建议。

表现：

- 浏览器断开、文件不存在、平台页面变化、人工标记失败等都可能表现为失败。
- 哪些失败可以一键重试，哪些需要人工处理，不够明确。
- 计划状态和条目状态可能不完全一致，需要人工理解数据模型。

### 6.4 扩展性仍需加强

项目已经有 `platforms` 协议和注册机制，但不同平台能力并不均衡。

表现：

- 百家号发布链路相对完整。
- B 站具备基础发布能力，但部分选择仍需人工确认。
- 小红书已有枚举和目录，但发布逻辑尚未完整实现。
- 平台能力、标题规则、封面规则、评论能力、自动提交能力还需要继续沉淀为统一配置和协议。

### 6.5 Web 端能力偏轻

系统已有 FastAPI，但目前更像接口基础设施，还不是运营可直接使用的产品界面。

表现：

- 没有统一“每日运营工作台”。
- 没有计划执行清单页面。
- 没有失败处理中心。
- 没有任务进度、日志和通知的集中展示。

## 7. 产品完善路线图

### 7.1 P0：易用性优先，让运营每天少想少查

P0 的目标是把已有能力包装成运营能稳定使用的工作台和执行清单。

建议功能：

- 每日运营工作台
  - 展示今日计划、计划状态、总任务数、成功数、失败数、待执行数。
  - 展示每个账号的待发布数、失败数、平台、账号名。
  - 展示待评论任务、待过审任务、下载/合成失败任务。

- 自动生成执行命令
  - 在计划详情中按账号生成 `plan run` 命令。
  - 支持一键复制单个账号命令。
  - 支持生成整份运营执行清单，适合发给运营人员。

- 一键日常流程入口
  - 以用户和品类为输入，串起采集、合成、创建计划、生成执行清单。
  - 每一步先给预览，再确认执行。
  - 输出明确：完成了什么、失败了什么、下一步做什么。

- 失败恢复中心
  - 按失败类型分组：文件缺失、浏览器问题、平台填充失败、人工失败、下载失败、合成失败。
  - 对可重试失败提供“重置后重跑”的明确入口。
  - 对不可自动修复失败提供人工处理建议。

P0 验收标准：

- 运营不需要手写 SQL 查询计划和账号任务。
- 运营不需要自己拼 `plan run` 命令。
- 每天打开工作台能知道今天是否已采集、已合成、已建计划、哪些账号未发布。
- 失败任务能在一个地方看到原因和下一步处理方式。

### 7.2 P1：扩展性增强，让新平台和新品类更容易接入

P1 的目标是减少平台差异散落在流程中的情况，让平台、账号、内容池和品类规则更配置化。

建议功能：

- 平台能力标准化
  - 继续完善 `platforms` 协议，将发布、评论、封面、标题、自动提交、回链、过审检查纳入清晰能力声明。
  - 平台能力在页面上可见：哪些支持自动提交，哪些需要人工确认，哪些支持评论。

- 平台状态分级
  - 百家号：标记为“可日常使用”。
  - B 站：标记为“半自动可用”，注明需要人工确认的环节。
  - 小红书：标记为“待实现”或“实验中”，避免运营误用。

- 配置化分配规则
  - 账号日限、账号品类、平台策略、视频池绑定尽量通过配置或后台管理。
  - 新增账号后无需改代码即可进入计划分配。
  - 新增品类后可配置引导视频、贴纸、评论话术、采集关键词。

- 标题和封面策略沉淀
  - 不同平台可定义标题长度、标签数量、封面要求、默认话题。
  - 打包和自动发布使用同一套标题/封面策略，减少结果不一致。

P1 验收标准：

- 接入新账号不需要工程改代码。
- 新品类上线只需要补配置和素材。
- 平台能力差异在产品侧清楚可见。
- 新平台接入时只需实现平台适配层，不改主流程。

### 7.3 P2：产品化与稳定性，让系统可长期运营

P2 的目标是把工具变成可多人协作、可监控、可维护的运营系统。

建议功能：

- 轻量 Web 前端
  - 基于现有 API 增加计划页、任务页、账号页、素材审核页、失败处理页。
  - 页面以运营效率为核心，不做复杂后台，只做高频任务闭环。

- 任务进度和日志
  - 发布、评论、合成等长任务展示进度。
  - 日志按计划、账号、任务聚合。
  - 关键失败可直接定位到任务和原因。

- 通知和统计看板
  - 企微通知覆盖计划完成、失败汇总、过审结果。
  - 统计看板展示发布量、成功率、失败率、过审率、互动数据。

- 定时任务
  - 支持定时采集、定时合成、定时检查过审、定时抓统计。
  - 对需要人工确认的发布环节仍保留人工介入。

- 多人协作和权限
  - 用户、账号、视频池、计划归属更明确。
  - 运营只看自己负责的账号和计划。
  - 管理员可看全局账号、配置和异常。

- 部署和数据安全
  - 明确环境变量、密钥、Webhook、AI Key 的配置方式。
  - 数据库备份策略。
  - 输出文件和下载文件清理策略。
  - 常见故障处理手册。

P2 验收标准：

- 系统可由多名运营同时使用，不互相干扰。
- 每天任务进展、失败、过审、统计都有可视化沉淀。
- 密钥和通知配置不写死在文档或业务流程里。
- 工程维护者可以通过日志和任务状态快速定位问题。

## 8. 下一阶段产品验收标准

如果要判断系统是否真正从 MVP 走向“简单、够用、好用”，建议使用以下验收标准：

- 简单
  - 新运营人员只需要理解“今日工作台 -> 执行清单 -> 浏览器确认 -> 失败处理”四件事。
  - 高频操作不需要写 SQL，不需要记账号 ID，不需要手动拼复杂命令。

- 够用
  - 能稳定覆盖采集、合成、计划、发布、评论、检查、统计的日常闭环。
  - 百家号作为主力平台可日常使用，B 站/小红书能力状态清楚，不误导运营。
  - 出现失败时有可执行的恢复路径。

- 好用
  - 系统主动告诉运营下一步该做什么。
  - 计划和账号任务清晰可见。
  - 执行命令自动生成，错误信息可读。
  - 常见问题有操作建议，而不是只给技术异常。

## 9. 产品边界

当前阶段不建议追求完全无人值守发布。原因是各内容平台的发布页、审核规则和风控策略变化频繁，保留人工确认能显著降低误发和风控风险。

更合理的产品边界是：

- 系统负责批量准备、自动填充、状态追踪和异常恢复。
- 运营负责关键确认、平台异常判断和内容质量把关。
- 工程负责平台适配、稳定性和自动化能力逐步增强。

这个边界能让产品先稳定服务日常运营，再逐步提高自动化比例。

## 10. 术语表

| 术语 | 含义 |
| --- | --- |
| 素材 | 从抖音等平台采集到的原始视频及元数据 |
| 合成任务 | 将素材加工成可发布视频的生产任务 |
| 发布计划 | 某天或某批次要发布的一组任务 |
| 计划条目 | 某个账号发布某条视频的具体任务 |
| 评论任务 | 发布成功后，对目标链接执行评论互动的任务 |
| 视频池 | 某个运营用户或账号组可使用的一批视频内容 |
| 平台适配 | 针对百家号、B 站、小红书等平台的发布、评论、回链实现 |
| 比特浏览器 | 用于多账号隔离和自动化发布的浏览器容器 |
